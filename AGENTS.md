# Repository instructions

- Read README and the relevant development/deployment guide before changes. Use English for source and repository documentation.
- Collect the relevant issues, decide a bounded plan, implement and verify. Use a separate worktree; leave adjacent repositories and primary checkouts unchanged.
- Preserve AGPL-3.0-only and third-party notices. Consume exact published Contracts packages; no sibling source imports or submodules.
- Use the pinned .NET 10 SDK (10.0.401, `global.json`) with central NuGet management and locked restores, and the documented commands. C# is the implementation language of every product surface (P2-021): the static Site, the Blazor WebAssembly profiles and the Razor class library. TypeScript is only the thin Cloudflare Worker adapter (`worker/index.ts`); Node runs wrangler and the reviewed policy checks. The server connection page only prepares the published Hello packaging example; business APIs, sessions, billing and AI execution remain outside this Web bootstrap.
- Keep PR checks credential-free. Never print or commit tokens or put private values in browser bundles. A Cloudflare API token belongs in the GitHub environment secret, not a client variable.
- Build and verify once, then deploy those same bytes. Distinguish mocked contract tests, local production-browser tests, real Cloudflare delivery and future C# product integration.
- Follow the user's authorization for remote settings/deployment. Do not merge a PR without authorization; under the Plan, the user's authorization of a range of tasks covers the coordinator's merges for those tasks.

## Flagship role

Web is an **active** repository of the ArcForges flagship ([AD-0001](https://github.com/ArcForges/ArcForges-Design/blob/main/docs/decisions/AD-0001-flagship-pivot.md)); the design authority is [ArcForges-Design](https://github.com/ArcForges/ArcForges-Design). Per [architecture 01 §5](https://github.com/ArcForges/ArcForges-Design/blob/main/docs/architecture/01-system-overview.md#5-repository-and-project-map), the [web experience](https://github.com/ArcForges/ArcForges-Design/blob/main/docs/experience/web.md) and the [reuse classification](https://github.com/ArcForges/ArcForges-Design/blob/main/docs/reuse/inventory-and-classification.md#4-web), it reuses the static Site generator, `ArcForges.Web.Ui`, the profile bundle and budget tooling, the Worker static-asset adapter and the guarded deploy. The public Site pages are rewritten for ArcForges, the `account` profile is adapted, the `fleet` profile is new and `ArcForges.Web.Operations` becomes the operator console. The Chat profile is retained and not routed (conflict C-12). Flagship surfaces deploy dark; publishing the public site and enabling production surfaces is Plan task AF-PROD-01 and needs the user's approval.

## Delivery (serial, ArcForges/Plan)

Tasks for this repository come from the [Plan delivery graph](https://github.com/ArcForges/Plan/blob/main/delivery-graph.json) and are delivered under the Plan [execution policy](https://github.com/ArcForges/Plan/blob/main/execution-policy.md) and [delivery procedure](https://github.com/ArcForges/Plan/blob/main/delivery-procedure.md) ([AD-0014](https://github.com/ArcForges/ArcForges-Design/blob/main/docs/decisions/AD-0014-delivery-method.md)). They are binding. The historical P2-018 model (delivery lanes, adoption slices, `delivery.py` claims and handoffs, parallel workers, integration-owner roles, Plan leases, the build slot and the launcher) is retired and never resumed.

- One task is active at a time. Work only inside its write scope, in a worktree `.worktree/<task-id-lower>` on branch `task/<task-id-lower>`, never in the primary checkout.
- Delegated workers and reviewers work locally. Only the coordinator pushes (through the pre-push verification), opens pull requests, merges (at the reviewed head, after the merge gate: the verification's PASS line for the owner's PRs, hosted CI for external PRs) and deploys through the guarded main-push path.
- Title pull requests `[<TASK-ID>] <summary>`.
- Shared files: the application shell owns root route registration, and each surface adds its own route module and per-origin edge directory; shared UI components live in `ArcForges.Web.Ui`. Lock files are regenerated after rebase, never hand-merged.
- Implemented baseline: the static Site generator, the canonical-host Worker and the Hello pages, with the WP02 build, dependency and provenance baselines; the Account and Chat profiles prove the session and gRPC-Web paths and are not a product yet; Operations is a skeleton.
- Earlier dated bootstrap and validation records under `docs/` describe their original scope; they are evidence, not execution instructions. Where older documents prefix a command with `delivery.py build-slot run … --` or assign a step to an integration owner, that is historical: run the wrapped command directly, and leave pushing and merging to the coordinator.

## Local verification (AD-0016)

The owner's (`deku2026`) PRs are verified by the repository's pre-push hook, not by hosted CI ([AD-0016](https://github.com/ArcForges/ArcForges-Design/blob/main/docs/decisions/AD-0016-local-first-verification.md)). The cross-repository rules are the Plan [AGENTS.md](https://github.com/ArcForges/Plan/blob/main/AGENTS.md) rules 6 and 7.

- **Install** once per clone, from the main checkout on `main`: `python eng/verify.py install`. It copies `.githooks/*` (the pre-push verification and the staged-whitespace pre-commit check) into the clone's common hooks directory, so every worktree runs them, and removes any `core.hooksPath`. Re-run it when `.githooks/` changes.
- `python eng/verify.py list` shows the profile and steps. `python eng/verify.py run` verifies `HEAD` now; the push reuses that pass for the identical commit, step set, scripts and tools (the secret scan, the Site and candidate source ref and the clone identity bind it to the exact base and head commits).
- **What runs.** Each pushed commit, never the working tree, as listed in `eng/verify_steps.py`: every validation job of `ci.yml` and the `candidate` that `deploy` ships, each on the host the hosted job used. Every change runs the full profile (the naming scan and the provenance inventory read Markdown too).
  - Lane `win`, in `<main checkout>/.worktree/_verify`: `Source (windows-latest)`: `npm ci --ignore-scripts` (with the npm bundled with the selected Node) and `node tooling/project.ts licence-evaluated`; then `C# restore, build, test and publish (windows-latest)`: for each project of `ci.yml`'s `CSHARP_PROJECTS` the locked restore, `dotnet format --verify-no-changes` and the Release build; the tests of `CSHARP_TEST_PROJECTS`; the App and Operations publishes; the static Site built twice and compared byte for byte.
  - Lane `wsl`, in the WSL Debian clone `~/.cache/arcforges-verify/Web`: `clone-identity` (the `origin` URL is this GitHub repository, which the naming scan requires, HEAD a local branch at the pushed commit and `origin/main` the merge base, which the provenance audit compares against; nothing is fetched from it), `npm ci --ignore-scripts`, `npm audit --audit-level=high` (from `quality`), the same C# steps as on Windows, `npm run check` (`Source (ubuntu-latest)`, with the Release tool of that build) and its evidence files; then `candidate`: a clean-tree test, the App publish, the profile budgets, the Worker and build identity emission, the sealed candidate built twice and compared, `node tooling/candidate.ts verify` and the profile bundle with its verification, at the local version `0.1.0-local`.
  - Lane `scan`: `git diff --check` over the pushed range and the pinned gitleaks image over the pushed range with `.gitleaks.toml`, without network. `actionlint` when `.github/workflows/**` changed.
  - Both lanes start from an empty `artifacts/`. `CI` and `GITHUB_*` are not set; the MSBuild properties that `CI=true` selects (`RestoreLockedMode`, `ContinuousIntegrationBuild`) are set directly, and `WasmNativeWorkload=false` keeps an installed `wasm-tools` workload out of the Blazor build, as on a hosted runner (with it, the publish relinks the runtime and breaks the profile budgets). Cloudflare credentials are unset and nothing contacts Cloudflare. Not reproduced: dependency review and CodeQL (GitHub services; external PRs, dispatch and the weekly schedule keep them). The browser test project stays local opt-in and is not part of the hook.
- **Prerequisites** (installs are the user's): on Windows, the .NET SDK selected by `global.json` with a workload set whose WebAssembly manifests match it (`win-workload-preflight`: the App's lock records the SDK's `Microsoft.NET.Sdk.WebAssembly.Pack`; workload set 10.0.401 for SDK 10.0.401), Node as pinned in `.node-version` with its bundled npm, PowerShell 7, Git and Python 3.14; in WSL Debian, the same .NET SDK, Node and npm as pinned (`.node-version`, `packageManager`), Python 3.14 and a running Docker Engine with the pinned gitleaks image; network access to the NuGet and npm registries.
- **Failures.** A failed, timed-out or unrunnable step rejects the push and prints the step, the last log lines and the log path (`<git common dir>/arcforges-verify/logs/`). Read the log, fix the cause, push again.
- AI agents must never use `git push --no-verify` to bypass required validation.
- They must also never disable, remove, modify, or otherwise circumvent the hooks merely to allow a push.
- If validation fails, investigate and fix the underlying issue.
- If a required local test cannot run, do not silently skip it or claim successful verification.
- Changing `eng/verify*.py` or `.githooks/` as reviewed engineering work is allowed; changing them to get a push through is not.

## Efficient execution

The Plan's rule 7 applies. In this repository:

- Install once (`npm ci --ignore-scripts`, `dotnet restore <project> --locked-mode` for the changed projects), then build incrementally: `dotnet build <project> --no-restore -c Release`.
- While iterating, run only the affected checks: the changed test project (`dotnet test <test-project> --no-build -c Release`, with `--filter-class` for one class), the changed Node test file (`node --test tests/provenance/<name>.test.ts` or `tests/worker/<name>.test.ts`), `npm run check:dependencies` after a bound input changed, `npm run typecheck` and `dotnet format <project> --no-restore --include <files>`.
- The full profile (both C# legs, `npm run check` and the candidate) runs once, through `python eng/verify.py run` before handover, so that the push reuses the pass.

## Hosted CI

- **Owner PRs:** no hosted validation or security analysis; `Source`, `C# restore, build, test and publish`, `Dependency audit and repository checks`, `Dependency review`, `CodeQL`, the candidate and `Verify` show as skipped. `Verify` is the required check (ruleset `protectmain`); a skipped `Verify` satisfies it.
- **External PRs** (Dependabot included) and manual dispatches: the full CI as before: both `Source` and both `C#` legs, `quality` (audit, actionlint, the full-history secret scan), dependency review (PRs), CodeQL for C#, JavaScript/TypeScript and Actions, the candidate after `source` and `quality`, and `Verify`, which requires every one of them. An external PR merges only when `Verify` passes and the code-scanning `CodeQL` check is not failing.
- **Main pushes:** delivery only: the candidate (with the main-push-only profile bundle upload), then `deploy`, which needs the candidate and keeps its environment, concurrency and steps. A broken candidate is caught before merge by the local profile, which builds it.
- **Schedule** (weekly): the security analysis: CodeQL and `quality` (dependency audit, actionlint and the full-history secret scan). No source, C# or candidate job.

## Required validation limits

Follow [validation policy](docs/validation-policy.md), which supersedes older runtime and release-test requirements. Its Design authority is the historical [CI and local validation policy](https://github.com/ArcForges/ArcForges-Design-Parallel/blob/64173614f2c41543bfff8f6df8d5a9e41207eb0a/docs/assurance/ci-and-local-validation-policy.md) (ArcForges-Design-Parallel at `64173614`), except its rule 9 (parallel delivery), which AD-0014 supersedes; where they differ from the Plan execution policy, the Plan governs. Never add or execute macOS CI, device/emulator/GUI/browser E2E CI, live service or inference CI, installed-consumer CI or public-download verification. Keep runtime checks explicit local opt-in. Do not repeat public archive/hash checks, passing tests or post-merge runtime cycles. Preserve lock/signature/licence/provenance checks at actual trust handoffs. Linux checks run in the local WSL2 Debian distribution through `wsl.exe -d Debian` on a Linux-native filesystem, never under `/mnt/c` (P2-024 supersedes the earlier wsl.exe prohibition); toolchains inside WSL are installed by the user. Do not configure proxy 7890 or install toolchains solely for testing. Diagnose network failures, retry ordinary ones with bounded backoff, inspect remote state before retrying a write, and report the exact operation if it persists (Plan execution policy §5). The pre-push verification (Local verification above) is the one place the full build, tests and candidate run before an owner PR merges; the pre-commit hook checks only the staged whitespace.

Dependency additions and upgrades follow [the enforced admission policy](docs/dependency-policy.md); update its input-bound review and retain the existing class and provenance gates.
