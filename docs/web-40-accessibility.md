# WEB.40 accessibility re-proof: axe-core and WCAG 2.2 AA

Status: recorded at run head 73173c2 (2026-10-09). This is local opt-in evidence (P2-017); no browser runs in CI. The coordinator re-runs the browser suites at the review head.

Requirement: P2-021 item 8 (brief section 10, adjudication of 2026-10-09). Before the React apps retire, every replacement screen and state needs axe-core and a recorded WCAG 2.2 AA checklist. This record covers Account (five states), Chat (four states), the App error banner (one state) and the four Site pages: 14 screen states in all. Focus placement (AX-02) is recorded separately in [web-40-ax-02-focus.md](web-40-ax-02-focus.md), which links here for the axe and checklist evidence. The retirement table is [web-40-react-retirement.md](web-40-react-retirement.md), and the Site parity record is [web-40-site-parity.md](web-40-site-parity.md).

## Method

**Run.** `LocalAccessibilityBrowserTests` in `tests/browser/ArcForges.Web.Browser.Tests` declares 10 tests, and they write the 14 rows below. The run at head 73173c2 recorded 10 passed, 0 failed and 0 skipped in the local run log, which is not committed. The suite runs only when `ARCFORGES_LOCAL_BROWSER=1`, the build directories are named and no CI marker is set (`LocalOptIn.cs:32-39`). It serves `artifacts/publish/app/wwwroot` (the Account and Chat profiles, published from `src/ArcForges.Web.App`) and `artifacts/site` (the C# static Site) through Playwright routes. The Account and Chat service answers are fixed by the test, so no server or live service is used.

**Tool versions.**

|---|---|---|
| axe-core | 4.13.0 | Bundled in `Deque.AxeCore.Commons` 4.13.0; its embedded script reads `axe.version="4.13.0"` |
| Deque.AxeCore.Playwright | 4.13.0 | `Directory.Packages.props:11` |
| Microsoft.Playwright (.NET) | 1.62.0 | `Directory.Packages.props:15`; test project only |
| Chrome | Not recorded for the run. The run log names neither the browser nor its version, and it does not show `ARCFORGES_CHROMIUM_PATH`. Playwright's own Chromium was not used by the focus run, because the Playwright build expects Chromium 1234 and that build is not installed on this machine (web-40-ax-02-focus.md, "Record of the local browser run").

**How axe ran.** `AssertAxeAsync` calls `Page.RunAxe()` with no options (`LocalAccessibilityBrowserTests.cs:326`), so the default rule selection applies and the axe-core script is the one bundled in the Deque package. The suite does not read `ARCFORGES_AXE_CORE_PATH`. Each screen asserts zero violations.

**Rules evaluated.** The bundled axe-core 4.13.0 rule set has 105 rules. The run evaluated 89 of them on every state. The 16 it did not evaluate are seven experimental rules (css-orientation-lock, focus-order-semantics, hidden-content, label-content-name-mismatch, p-as-heading, table-fake-caption, td-has-header) and nine others (aria-roledescription, audio-caption, color-contrast-enhanced, duplicate-id, duplicate-id-active, identical-links-same-purpose, landmark-complementary-is-top-level, meta-refresh-no-exceptions, target-size). Two of the nine map to criteria in scope: target-size (2.5.8, AA) and audio-caption (1.2.1, tagged deprecated). The other seven are deprecated, obsolete or AAA. The report does not record why these rules were not evaluated, so the rows for 2.5.8 do not use axe.

**Recording.** Each state appends two lines to the file named by `ARCFORGES_A11Y_REPORT`. The first holds the screen, the state, the URL and the counts of violations, passes, incomplete and inapplicable rules. The second names the sorted rule IDs that passed, were incomplete, were inapplicable and were violated. The rule lines let each pass (axe) cell be checked against the rules that actually passed on that state.

**Reproduce.** Set `ARCFORGES_LOCAL_BROWSER=1`, `ARCFORGES_PROFILE_DIR` (the published Account and Chat `wwwroot`), `ARCFORGES_SITE_DIR` (the Site output), `ARCFORGES_CHROMIUM_PATH` (an installed Chrome or Edge) and `ARCFORGES_A11Y_REPORT`, with CI markers unset. Then run `dotnet test tests/browser/ArcForges.Web.Browser.Tests --no-build -c Release --filter FullyQualifiedName~LocalAccessibilityBrowserTests`.

**Status values.** Each checklist cell holds exactly one of five values.

- `pass (axe)`: a rule mapped to the criterion (its WCAG tag in the axe 4.13.0 rule metadata) is in that state's passed list. A rule that was inapplicable on a state cannot support `pass (axe)` there.
- `pass (inspection)`: checked by reading the Razor sources, CSS and Site HTML. The file and line are cited. Nothing was rendered.
- `pass (browser test)`: asserted by a test in `LocalAccessibilityBrowserTests` that drives the page and checks the criterion itself, and that the run recorded as passed. This value is added for this record, because one assertion (keyboard operation of the banner Dismiss) is neither axe nor inspection. It is used only for 2.1.1 on E1.
- `not applicable`: the reason is given in the Basis column.
- `not verified: needs a human assistive-technology session`: used where the criterion needs a screen reader, a judgement or a manual rendered check (reflow, target spacing, a focus overlap). It is also used where inspection found a likely failure, which is named under Open issues. There is no separate fail value, so this is the only value that stands in for a failure.

**Derivation.** Where a criterion has mapped rules, a cell is `pass (axe)` when a mapped rule passed on that state, and otherwise it keeps the inspection status. Cells that stay `not verified` where a rule does apply are judgements the rule cannot settle: 2.4.4 on S1 to S3 (link-name passes there, but the purpose of Source in context is a judgement). The 1.4.1 cells on C1, C3 and C4 have no passing rule, because the grey Cancel state is a colour change that axe does not test. The checklist was generated from the rule lines, the axe tags and the criterion data, and every `pass (axe)` cell was checked against the passed list of its state.

**Limits.** axe covers only part of WCAG 2.2. No rule in the run is tagged with 1.3.2, 1.3.3, 1.4.5, 1.4.10, 1.4.11, 1.4.13, 2.1.2, 2.4.5, 2.4.6, 2.4.7, 2.4.11, 2.5.7, 3.2.6, 3.3.3, 3.3.4, 3.3.7, 3.3.8 or 4.1.3, so their rows rest on inspection, judgement, a browser test or not applicable. The three rules tagged 2.1.1 (frame-focusable-content, scrollable-region-focusable and server-side-image-map) are inapplicable on every state, so 2.1.1 rests on inspection and the banner browser test. The experimental rules that map to 1.3.4 (css-orientation-lock), 2.4.3 (focus-order-semantics) and 2.5.3 (label-content-name-mismatch) are not run. The 2.2 criteria 2.4.11, 2.5.7, 3.2.6, 3.3.7 and 3.3.8 have no axe rule.

**Not done in this record.** No browser was started, no screenshot was taken and nothing was rendered for this record. The results are those of the recorded run at 73173c2. The bUnit suites, `HostPageAccessibilityTests` and `LocalFocusBrowserTests` were not re-run here. The contrast ratios were recomputed from the hex values in `app.css` and the Site stylesheet.

## Open issues

These are real accessibility issues or likely failures, or judgements that need a person, found by reading the sources or by the review. Nothing here was changed in this record. Each names the file and line, and the checklist rows carry the status.

1. **Skip link may cover the brand when focused (1.4.13, possible).** The focused skip link sits 12 px from the top and 24 px from the left (`app.css:81-91`, `app.css:90`). By geometry it covers the top edge of the brand (header 112 px, `app.css:53`; brand at 64 px, `app.css:60-70`). This is not rendered. Check it visually.
2. **Static Site controls look enabled but cannot be used (3.3.2 and usability; not an axe violation).** On `/hello/`, the name field and Say hello (`HelloExample.razor:1`), and on `/cloud-hello/`, Check connection (`CloudHelloExample.razor:2`), are rendered `disabled`. The static output cannot enable them: the Site has no script, since the C# pages carry no script element and the CSP is `script-src 'self'` (`docs/web-40-site-parity.md`). `site.css` has no disabled rule, so the buttons keep their enabled green fill. Their noscript text tells a visitor to enable JavaScript, which is wrong for a visitor who has JavaScript on and then sees controls that do nothing. This is not a 1.4.1 failure, because colour carries no information on those controls; the missing visual state is the issue.
3. **Nested live regions in Account (4.1.3, check with AT).** The failure paragraph is `role=alert` (`Account.razor:24`) inside a `role=status aria-live=polite aria-atomic=true` panel (`Account.razor:13`). Assistive technology may announce the failure twice, or as a plain status update.
4. **Session expiry shown with no warning or extension (2.2.1, judgement).** Signed-in Account states show Session ends and Idle expiry (`Account.razor:41-44`). The page gives no warning and no way to extend the session. Whether this is a time limit under 2.2.1 is a judgement; the server rule is not inspected.
5. **No link between Account and Chat (2.4.5, judgement).** `ProfileLayout.razor:3-14` has no navigation. Each App page is reached only by typing its path. Whether the profile counts as a set of pages under 2.4.5 is a judgement.
6. **Chat failure notice names no field and no correction (3.3.1 and 3.3.3, judgement).** The failed-send notice (C4) reports the failure in the transcript, for example `The server rejected the request.` (`ProbeFailure.cs:40`). It does not name the Name field or say how to send again. C4 is recorded as not verified for 3.3.1 and 3.3.3.
7. **Chat Name field has no autocomplete token (1.3.5, judgement).** `Chat.razor:16`. If the field collects the user's own name, it needs an input purpose. The `/hello/` field sets `autocomplete="off"` (`HelloExample.razor:1`), which is not an identified purpose either.
8. **Chat Cancel state shown by colour alone (1.4.1, judgement).** While idle, after a reply and after a failed send, Cancel is grey with `aria-disabled` (`app.css:161-166`, `Chat.razor:19`). The change to grey is the only visual cue.
9. **Site link named only by context (2.4.4, judgement).** `Shell.razor:1` labels a link `Source`, and its purpose depends on the nav around it. It appears on S1 to S3.
10. **Banner Dismiss: visible glyph and accessible name differ (2.5.3, judgement; new).** The visible text of the banner's Dismiss is the glyph `×` (`index.html:17`, `&times;`), and its accessible name is `Dismiss`. Under 2.5.3 the name should contain the visible text, so this turns on whether a glyph is a label. A fix would make the visible text match the name, or add a visible word. Not changed here.
11. **Banner is fixed to the bottom edge and can cover focused content (2.4.11, judgement; new).** `#blazor-error-ui` is `position: fixed` at the bottom with `z-index: 1000` (`app.css:442-451`), and it appears on an unhandled error. When shown it can cover other focus targets on the page. The focused element in E1 is the banner's own Dismiss, so the recorded state is not affected.
12. **Site header links and back links are about 21 px tall (2.5.8, manual measurement; new).** The header nav links and the back links use 14 px text at a 1.5 line height, which is about 21 px (`site.css`). Below the 24 px minimum, they need the spacing exception, which needs a hand measurement. Not verified.
